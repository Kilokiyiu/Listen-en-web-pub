## 1. 消息队列是什么

**消息队列（Message Queue，MQ）** 是一个中间件，充当服务之间的「邮局」：

```
发送方（Producer）  →  把消息投进队列  →  消息队列  →  接收方（Consumer）按自己节奏取走处理
```

关键特征：

- **异步**：发送方投递消息后可以立刻返回，不必等接收方处理完
- **解耦**：发送方不需要知道有哪些接收方、接收方是否在线
- **缓冲**：流量高峰时，消息暂存在队列里，消费者慢慢消化

### 生活中的类比

| 场景 | 对应关系 |
|------|----------|
| 你寄快递 | Producer 发布消息 |
| 快递分拣中心 | Exchange（交换机） |
| 各小区快递柜 | Queue（队列） |
| 收件人取件 | Consumer 消费消息 |
| 快递单号 / 地址 | RoutingKey（路由键） |

## 2. 为什么需要消息队列

### 2.1 四个核心价值

| 价值 | 说明 | 本项目例子 |
|------|------|------------|
| **解耦** | 服务之间不直接依赖 | 注册成功后 IdentityService 不必知道 ListenService 的存在 |
| **异步** | 耗时操作不阻塞主流程 | 发邮件、初始化数据放到后台处理 |
| **削峰** | 抵抗流量尖峰 | 1 万人同时注册，队列缓冲后再慢慢处理 |
| **可靠** | 消息持久化、失败重试 | RabbitMQ 持久化 + 手动 ACK |

### 2.2 什么时候该用、什么时候不该用

**适合用 MQ：**

- 操作完成后有「副作用」但不必立刻完成（发邮件、写统计、同步缓存）
- 多个服务需要知道同一件事（用户注册、订单支付）
- 任务耗时长（转码、生成报告、批量导入）
- 流量波动大

**不适合用 MQ：**

- 必须立刻返回结果（登录验证、查余额、实时搜索）
- 业务简单、流量低、服务少（HTTP 直调更简单）
- 强一致性要求（转账扣款必须同步确认）

**经验法则：** 先 HTTP，等出现「慢、多、耦合紧、扛不住峰值」再引入 MQ。

## 3. 核心概念

### 3.1 基础术语

| 术语 | 英文 | 含义 |
|------|------|------|
| 生产者 | Producer | 发送消息的服务 |
| 消费者 | Consumer | 接收并处理消息的服务 |
| 消息 | Message | 传递的数据（通常是 JSON） |
| 队列 | Queue | 存储消息的缓冲区 |
| 交换机 | Exchange | 决定消息路由到哪个队列 |
| 路由键 | Routing Key | 消息的路由标识 |
| 绑定 | Binding | Exchange 和 Queue 之间的关联规则 |

### 3.2 消息流转（以本项目为例）

```
IdentityService
    │
    │  Publish("Identity.UserCreated", { UserId, UserName, Email })
    ▼
Exchange: listen_en_web_events  (Direct 类型)
    │
    │  RoutingKey = "Identity.UserCreated"
    ├──────────────────────┐
    ▼                      ▼
Queue: identity-service   Queue: listen-service
    │                      │
    ▼                      ▼
（本服务 Handler）      UserCreatedEventHandler
```

### 3.3 两种常见消息语义

| 类型 | 含义 | 例子 |
|------|------|------|
| **事件（Event）** | 「某事已发生」，发布者不关心谁处理 | `Identity.UserCreated` |
| **命令（Command）** | 「请做某事」，通常指定一个处理者 | `TranscodeAudio { FileId }` |

本项目采用的是 **集成事件（Integration Event）** 模式——跨服务之间传递「发生了什么」。

## 4. 消息队列 vs HTTP 直调

### 4.1 对比表

| 维度 | HTTP 同步调用 | 消息队列 |
|------|---------------|----------|
| 耦合度 | 高（要知道对方地址和接口） | 低（只发事件，不关心消费者） |
| 响应速度 | 等对方处理完才返回 | 投递即返回 |
| 一致性 | 强一致（立刻知道结果） | 最终一致（可能延迟几秒） |
| 失败处理 | 对方挂了直接失败 | 消息暂存，稍后重试 |
| 复杂度 | 低 | 高（多一个中间件要运维） |
| 调试 | 调用链清晰 | 需要查队列、日志 |

### 4.2 时序对比

**HTTP 同步（注册 + 初始化词本）：**

```
用户 → IdentityService → ListenService → WordService → 返回用户
       ───────────── 全部串行等待 ─────────────
       总耗时 = 各服务耗时之和
```

**MQ 异步（注册 + 发事件）：**

```
用户 → IdentityService → 返回「注册成功」（几百 ms）
              │
              └──► MQ ──► ListenService 后台初始化
                    └──► WordService 后台初始化
```

## 5. 常见消息中间件对比

| 产品 | 特点 | 适用场景 |
|------|------|----------|
| **RabbitMQ** | 功能全面、易上手、支持多种 Exchange 类型 | 中小型微服务、事件驱动（**本项目选用**） |
| **Kafka** | 超高吞吐、消息可回溯、适合日志流 | 大数据、日志采集、事件溯源 |
| **Redis Stream** | 轻量、已有 Redis 时可复用 | 简单队列、低延迟场景 |
| **Azure Service Bus** | 云原生、与 Azure 深度集成 | 部署在 Azure 的项目 |
| **RocketMQ** | 阿里开源，国内文档丰富 | 国内大型互联网项目 |

**为什么 Listen-en-web 选 RabbitMQ？**

- 微服务规模适中，不需要 Kafka 级别的吞吐量
- Direct Exchange + RoutingKey 天然适合「按事件名路由」
- 自带 Management 管理界面，学习调试方便
- .NET 生态有成熟的 `RabbitMQ.Client` 库

## 6. RabbitMQ 深入

### 6.1 四种 Exchange 类型

| 类型 | 路由规则 | 使用场景 |
|------|----------|----------|
| **Direct** | RoutingKey 完全匹配 | 按事件名精确路由（**本项目**） |
| **Fanout** | 广播到所有绑定的队列 | 全员通知 |
| **Topic** | RoutingKey 模式匹配（`*.created`） | 按类别订阅 |
| **Headers** | 按消息头匹配 | 较少使用 |

本项目 Exchange 配置：

```csharp
// RabbitMQEventBus.cs
publishChannel.ExchangeDeclare(options.ExchangeName, ExchangeType.Direct, durable: true);
```

### 6.2 Queue 的关键属性

| 属性 | 本项目设置 | 含义 |
|------|------------|------|
| `durable` | `true` | 队列持久化，RabbitMQ 重启后仍在 |
| `exclusive` | `false` | 允许多个连接访问 |
| `autoDelete` | `false` | 没有消费者时也不自动删除 |

### 6.3 消息的 ACK 机制

**ACK（Acknowledgement）= 消费者告诉 RabbitMQ「我处理完了，可以删这条消息」**

| 模式 | 行为 | 风险 |
|------|------|------|
| **自动 ACK** | 消息一投递就删除 | 处理中途崩溃 → 消息丢失 |
| **手动 ACK** | 处理成功才确认删除 | 更安全（**本项目**） |

本项目逻辑：

```csharp
// 处理成功
consumeChannel.BasicAck(ea.DeliveryTag, multiple: false);

// 处理失败，重新入队
consumeChannel.BasicNack(ea.DeliveryTag, multiple: false, requeue: true);
```

### 6.4 消息持久化

仅队列持久化不够，消息本身也要持久化：

```csharp
properties.Persistent = true;  // DeliveryMode = 2
properties.ContentType = "application/json";
```

## 7. 事件驱动架构

### 7.1 两种「事件」的区别

| 类型 | 范围 | 例子 |
|------|------|------|
| **领域事件（Domain Event）** | 单个服务内部 | 「订单实体已创建」（不跨服务） |
| **集成事件（Integration Event）** | 跨服务通信 | `Identity.UserCreated`（通过 MQ 传递） |

### 7.2 本项目的分层

```
┌─────────────────────────────────────────────┐
│  业务层：LoginController.RegisterAsync       │
│  → eventBus.Publish("Identity.UserCreated") │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│  抽象层：IEventBus / IIntegrationEventHandler│
│  → 定义发布和订阅的契约                       │
└──────────────────────┬──────────────────────┘
                       ▼
┌─────────────────────────────────────────────┐
│  基础设施层：RabbitMQEventBus               │
│  → 连接 RabbitMQ、序列化、ACK               │
└──────────────────────┬──────────────────────┘
                       ▼
                  RabbitMQ Broker
```

### 7.3 为什么事件数据传 JSON 字符串，而不是共享 C# 类？

```csharp
// IIntegrationEventHandler.cs
Task Handle(string eventName, string eventData);  // JSON 字符串，不是强类型
```

原因：

1. **各服务独立部署**，不应共享同一个 Event 类库（否则改一个类所有服务都要重新发布）
2. **各服务可以有不同的 DTO**，只要 JSON 字段约定一致即可
3. ListenService 定义自己的 `UserCreatedEvent`，IdentityService 发匿名对象，互不影响

### 7.4 事件命名规范

```
{服务域}.{事件名}
```

| 事件名 | 含义 |
|--------|------|
| `Identity.UserCreated` | 用户注册成功 |
| `IdentityService.User.Created` | 管理员创建用户 |
| `IdentityService.User.PasswordReset` | 密码重置 |
| `Listening.EpisodePublished` | 听力材料发布（可扩展） |

常量定义在 `IntegrationEventNames.cs`，避免手写字符串拼错。

## 8. 结合本项目的代码走读

### 8.1 发布事件（Producer）

文件：`IdentitySerivce/.../LoginController.cs`

```csharp
// 1. 注入 IEventBus
public LoginController(..., IEventBus eventBus) { ... }

// 2. 业务完成后发布
eventBus.Publish(IntegrationEventNames.IdentityUserCreated, new
{
    UserId = user.Id,
    UserName = user.UserName,
    Email = req.Email
});
// 3. 立刻 return Ok()，不等 ListenService 处理
```

### 8.2 订阅事件（Consumer）

文件：`ListenService/.../Events/UserCreatedEventHandler.cs`

```csharp
[EventName(IntegrationEventNames.IdentityUserCreated)]  // 声明监听哪个事件
public class UserCreatedEventHandler : JsonIntegrationEventHandler<UserCreatedEvent>
{
    public override Task HandleJson(string eventName, UserCreatedEvent? eventData)
    {
        // 收到 JSON 后自动反序列化为 UserCreatedEvent
        logger.LogInformation("New user: {UserId}", eventData?.UserId);
        return Task.CompletedTask;
    }
}
```

### 8.3 自动注册（DI 扩展）

文件：`EventBusServiceCollectionExtensions.cs`

```csharp
// Program.cs 一行注册
builder.Services.AddEventBus(builder.Configuration, "listen-service", typeof(Program).Assembly);

// 内部做了三件事：
// 1. 扫描程序集中所有 IIntegrationEventHandler 实现类
// 2. 读取 [EventName] 特性，建立订阅关系
// 3. 启动 RabbitMQEventBus 作为 HostedService 开始消费
```

### 8.4 完整调用链

```
1. 用户 POST /api/identity/Login/RegisterAsync
2. IdentityService 写数据库
3. eventBus.Publish → JSON 序列化 → RabbitMQ Exchange
4. Exchange 按 RoutingKey 路由到 listen-service 队列
5. ListenService 的 RabbitMQEventBus 收到消息
6. 创建 DI Scope → 解析 UserCreatedEventHandler
7. JSON 反序列化 → HandleJson 执行业务
8. BasicAck 确认消费成功
```

## 9. 动手实验

### 实验 1：观察消息流转

**准备：**

```bash
docker run -d --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:3-management
```

**步骤：**

1. 启动 IdentityService 和 ListenService
2. 打开 http://localhost:15672（guest / guest）
3. 进入 **Exchanges**，找到 `listen_en_web_events`
4. 进入 **Queues**，应看到 `identity-service` 和 `listen-service`
5. 调用注册接口
6. 观察队列的 **Ready / Unacked / Total** 数字变化
7. ListenService 控制台出现 `Received user registration event`

### 实验 2：模拟消费失败

在 `UserCreatedEventHandler.HandleJson` 里临时加：

```csharp
throw new Exception("模拟处理失败");
```

观察：

- 消息被 Nack 并 requeue
- RabbitMQ 管理界面中该消息反复出现（重试）
- 修复代码后消息最终被正常消费

### 实验 3：自己写一个 Handler

在 ListenService 新增：

```csharp
[EventName(IntegrationEventNames.IdentityUserCreated)]
public class MyTestHandler : JsonIntegrationEventHandler<UserCreatedEvent>
{
    public override Task HandleJson(string eventName, UserCreatedEvent? data)
    {
        Console.WriteLine($"[MyTest] 收到用户 {data?.UserName}");
        return Task.CompletedTask;
    }
}
```

重启服务，注册一个用户，验证日志输出。  
（同一事件可以有多个 Handler，都会被执行。）

### 实验 4：用管理界面手动发消息

1. RabbitMQ 管理界面 → Queues → `listen-service`
2. 点击 **Publish message**
3. Payload 填入：

```json
{"UserId":"00000000-0000-0000-0000-000000000001","UserName":"test","Email":"test@example.com"}
```

4. Routing Key 填 `Identity.UserCreated`
5. 观察 ListenService 是否收到

## 10. 必知必会：可靠性设计

### 10.1 幂等性（Idempotency）

**问题：** 网络抖动可能导致同一条消息被投递多次。

**要求：** 同一个事件处理多次，结果和处理一次相同。

```csharp
// ❌ 错误：每次消费都 +1，重复消费会多加
await db.ExecuteAsync("UPDATE stats SET count = count + 1 WHERE event = @id", ...);

// ✅ 正确：先检查是否已处理
if (await db.ExistsAsync("SELECT 1 FROM processed_events WHERE id = @id"))
    return;
await DoWork();
await db.InsertAsync("processed_events", id);
```

本项目接口注释已强调：

```csharp
// 因为消息可能会重复发送，因此 Handle 内的实现需要是幂等的
Task Handle(string eventName, string eventData);
```

### 10.2 最终一致性

引入 MQ 后，系统从「强一致」变为「最终一致」：

```
T0: 用户注册成功（IdentityService 数据库已有记录）
T1: 事件进入队列
T2: ListenService 收到事件，初始化学习记录
```

T0 到 T2 之间可能有 **几百毫秒到数秒** 的延迟。  
前端不应假设「注册完立刻能在 ListenService 查到数据」。

### 10.3 消息顺序

RabbitMQ **不保证** 全局有序，只保证同一队列内 FIFO（单消费者时）。  
如果业务依赖顺序（先创建后更新），应：

- 用同一个 RoutingKey + 单消费者
- 或在消息中带版本号 / 时间戳，消费者自行判断

### 10.4 死信队列（DLQ）

消息多次重试仍失败时，应转入 **Dead Letter Queue** 而非无限 requeue：

```
正常队列 → 重试 3 次失败 → 死信队列 → 人工排查 / 告警
```

> 本项目当前尚未实现 DLQ，列为后续优化项。

## 11. 常见坑与最佳实践

### 11.1 常见坑

| 坑 | 现象 | 解决 |
|----|------|------|
| 忘记开 RabbitMQ | 服务启动报错连接失败 | Docker 先启动 rabbitmq，或加重试逻辑 |
| 队列名冲突 | 多环境共用同一个队列 | 开发/测试/生产用不同 queueName 前缀 |
| 大消息体 | 传文件二进制进 MQ | 消息只传 ID 或 URL，不传文件本身 |
| 同步思维写异步 | 注册完立刻查 ListenService 没数据 | 接受最终一致，或前端轮询 |
| 不做幂等 | 重复消费导致重复发邮件/重复扣款 | 用 processed_events 表或唯一约束 |
| 在 Handler 里做长事务 | 消费慢、队列堆积 | 快 ACK + 异步处理，或拆分小消息 |

### 11.2 最佳实践清单

- [ ] 消息体尽量小（传 ID，不传大对象）
- [ ] 事件名用常量（`IntegrationEventNames`），不要魔法字符串
- [ ] Handler 必须幂等
- [ ] 手动 ACK，处理成功再确认
- [ ] 消息和队列都持久化（`durable = true`）
- [ ] 每个服务独立队列，不要多个服务共用一个队列
- [ ] 记录日志：发布时 log eventName，消费时 log eventName + 关键 ID
- [ ] 监控队列深度（消息堆积 = 消费者处理不过来）
